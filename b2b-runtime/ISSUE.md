# [FEAT] B2B 축제별 독립 실행 환경과 운영 자동화 기반 분리

## Background (배경 및 문제점)

현재 B2B가 B2C의 게스트 인증, 네컷 업로드, MySQL, Redis와 배포 경로를 사용한다. 축제 트래픽이나 부하 시험이 기존 앱에 영향을 주지 않도록 실행 환경을 분리해야 한다. 축제마다 서버와 데이터베이스를 준비하고 검증한 뒤 행사 기간에 운영하며, 사진은 B2B 공용 S3에 보관한다.

## Proposed Solution (해결 방안)

- B2C 소스, 설정, DB, S3, 배포 workflow는 수정하지 않는다.
- `b2b-runtime/`에 독립 Gradle 앱을 둔다. 기존 네컷/프레임 엔진은 출처가 고정된 사본으로 재사용하고, 게스트 인증과 HTTP 진입점은 B2B 전용으로 구성한다. 후속 저장소명은 `peakpic-b2b-server`를 권장한다.
- 하나의 런타임은 하나의 projectId/slug에만 바인딩한다. 인증·생성·조회·업로드 경로 모두 `/projects/{slug}` 아래 둔다. B2C JWT와 다른 축제 JWT는 거절한다.
- 축제별 MySQL/Redis를 사용하고 B2B S3 경로는 `b2b/{environment}/{projectId}/{runtimeId}/`로 분리한다. DB를 새로 만드는 경우 runtimeId도 새로 발급한다. IAM도 이 범위로 제한한다.
- 참여 주소 `https://peakpic.app/go/{slug}/{code}`와 프레임 1~3개/사진 창 4개 계약을 유지한다.
- 운영 자동화는 설정 등록 → 환경 준비 → 이미지 배포 → readiness → 부하 시험 → 승인된 용량으로 공개 → 행사 종료 → 보관 기간 동안 조회 유지 → 정리 순으로 구성한다.
- 예상 인원은 부하 시나리오 입력이다. 시험 결과 없이 인원수만으로 서버 용량을 보장하거나 운영으로 자동 승격하지 않는다. 자원 상한을 함께 입력한다.
- 스테이징은 `t3.micro 2대`와 확인된 운영 RDS/Redis 사양에서 시작한다. 통과하면 그대로 사용하고, 실패하면 앱 수 2→4, 인스턴스 타입, DB 등 병목 하나씩 변경하며 재측정한다.
- 설정과 실측 숫자를 독립 저장소 기준 `load-test/results/`에 매번 남긴다. T3 크레딧, 메모리, DB 연결/IO, Redis, 완료율/지연을 함께 본다.
- 게스트 발급 IP 한도를 반드시 함께 시험한다. 행사장 Wi-Fi/통신사 NAT의 정상 참가자 429를 성능 부족과 분리하고, 서버 수가 바뀌어도 Redis의 공통 한도가 유지되는지 확인한다. 위조 XFF 우회와 refresh/창 만료 회복도 검증한다.
- 검증된 B2B 운영 ASG 수량은 행사 전/후 별도 예약으로 늘리고 2대로 복귀한다. 인스턴스 타입·RDS 상향/복귀는 전날/행사 후 사람이 수행한다. 결과 보관 후 test 환경만 정리한다.

## Alternatives Considered (대안)

- 기존 B2C 서버만 증설: 인증/DB/Redis 부하와 배포 장애가 공유된다.
- 축제별 DB 스키마만 분리: 같은 DB 인스턴스의 CPU/연결 수/IO는 공유되어 부하 격리가 충분하지 않다.
- B2C S3 버킷 공유: 기술적으로 가능하나 공통 수명주기·CORS·권한 변경이 기존 앱에 영향을 줄 수 있어 B2B 버킷을 새로 둔다.
- 처음부터 이미지 업로드를 presigned PUT으로 교체: 기존 검증과 업로드 동작을 먼저 재사용하고 실측 후 결정한다.

## Acceptance Criteria (인수 조건)

- [ ] 기존 앱 빌드 입력과 운영 배포 workflow에 변경이 없다.
- [ ] 독립 앱에서 게스트 발급/갱신 → 프레임 선택 → 네컷 생성 → 사진 업로드/조회가 동작한다.
- [ ] 다른 축제/issuer의 JWT, 다른 slug, B2C 경로를 통한 접근이 거절된다.
- [ ] 동일한 숫자 세션 ID가 다른 축제 DB에 있어도 S3 조회/삭제 범위가 겹치지 않는다.
- [ ] 프레임 1~3개, 선택 당시 프레임 고정, 기존 응답/오류 메시지 계약을 검증한다.
- [ ] B2B 전용 CI와 독립 실행 설명, FE 전환 계약을 제공한다.
- [ ] baseline 2대부터 한 설정씩 변경한 실험 이력과 T3 크레딧·지연·DB/Redis 관측이 남는다.
- [ ] IP별/전체 발급 한도의 429가 구분되고, 공용 IP의 정상 참여 거절 여부와 위조 헤더 우회·회복을 검증한다.
- [ ] B2B 전용 ASG의 행사 전 증설/종료 후 2대 복귀와 test 자원만의 정리를 검증한다.
- [ ] 전용 AWS 자격 증명·새 DB/Redis/S3로 실환경 검증을 완료한다.
- [ ] 중앙 관리자에서 환경 생성·부하 시험·공개·보관 종료를 추적하는 운영 흐름을 연결한다.
