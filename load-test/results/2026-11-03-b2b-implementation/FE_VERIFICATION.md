# #219 FE 확인 결과와 부하 모델의 차이

2026-11-03 전달받은 `peakpic-b2b-admin` 커밋 `4d2c6e8` 운영 반영 보고를 기록한다. 운영 배포 및 브라우저 실측은 FE 측 보고이며, BE에서 재실행한 결과와 구분한다.

## FE가 확인한 요청 제어

- 게스트 JWT는 localStorage에서 재사용한다. exp 30초 전 refresh하며 401/403은 refresh 후 요청당 한 번만 재시도한다. 발급·갱신은 동시에 하나만 진행한다.
- 네컷 생성은 첫 클릭부터 성공 후 페이지 이동까지 잠근다. FE 실측에서 5회 연타에 POST 1회였으며, 이번 점검에서 발견해 수정했다고 보고했다.
- 조회는 기본 5초 주기다. 탭이 보이지 않거나 업로드 중이면 요청하지 않고, 다시 보이면 즉시 한 번 조회한다. 페이지 이탈 시 타이머를 해제한다.
- setTimeout 사슬로 앞 조회 완료 후 다음 조회를 예약한다.

## 429 안내 확인

전달된 보고서의 2번 문장이 중간에 잘려 오류 처리 전체와 재시도 검증 결과는 확인 대기다. 대신 해당 FE 커밋의 `api.ts`, `frame-picker.tsx`를 읽어 다음 계약 차이를 확인했다.

- FE는 `Retry-After`가 있으면 해당 대기 시간을, 없으면 "잠시 후"를 표시한다. 현재 BE의 CustomException 응답에는 `Retry-After`가 없다. 따라서 FE의 대기 초수를 서버가 제공한다고 단정하지 않는다.
- 검토한 `4d2c6e8`의 FE 생성 화면은 모든 429를 참여자가 많다는 안내로 바꿨다. BE의 `FillWriteGuard`는 요청 속도 초과 외에 `FILL_TOO_MANY_SESSIONS`도 429로 반환한다. 후자는 활성 네컷 수 상한(기본 20개)이며 짧은 재시도 대기로 해소되는 조건이 아니다.
- 2026-11-03 FE 후속 답변: "429에 message를 넣어 주면 그대로 표시한다." BE의 `GlobalExceptionHandler`는 이미 `{status, message}`로 반환하며 아래 두 문구가 구분된다. 이 계약을 위해 추가 BE 변경은 필요 없다. FE 후속 반영 커밋과 운영 표시를 BE에서 재검증한 것은 아니다.
  - 요청 횟수 초과: `요청이 너무 잦습니다. 잠시 후 다시 시도해주세요`
  - 활성 세션 총량 초과: `진행 중인 함께 채우기 세션이 너무 많습니다 (최대 20개). 끝난 세션을 지워주세요`
- FE는 서버 `message`가 있으면 우선 표시하고, 없을 때만 일반 안내로 대체한다. 향후 오류 코드 필드나 정확한 대기 시간이 필요하면 별도 API 계약으로 정한다. 이 기록에서는 응답 구조나 운영 한도를 바꾸지 않았다.

## k6와 비교할 때의 가정

- 현재 k6는 매 네컷 흐름마다 새 게스트를 발급한다. FE의 기존 JWT 재사용 비율을 재현하지 않으므로 실제 참여 인원과 인증 발급량을 동일시하지 않는다. 공용 IP 신규 인증 유입은 별도 시험한다.
- k6는 JWT 만료 전 refresh를 처리하지만 401/403 발생 뒤 FE의 한 번 재시도까지 재현하지 않는다.
- k6는 화면이 보이는 참여자를 가정해 대기 중 조회하며 업로드와 조회를 겹치지 않게 한다. 백그라운드 전환·복귀 및 중복 클릭은 브라우저 검증 항목이다.
- 업로드 실제 사진 크기·해상도·형식, 참여 완료 소요 시간, 완성 후 조회 정책 및 브라우저 합성·다운로드 결과는 이번에 받은 범위에서 확인되지 않았다.
- 이 FE 확인 결과만으로 운영 수용 인원을 판정하지 않는다.
