# 외부 인증 서버 장애 전염 실험 (2026-09-03, #125)

조건: 로컬 부하 환경(t3.micro 근사, cpus 2.0/1GB). 가짜 침묵 카카오(모든 요청 120s 슬립)에
`kakao.user-info-uri`를 겨냥. 공격 200 VU(카카오 로그인 연타 = 톰캣 기본 스레드 수와 일치) +
방관자 10 VU(카카오와 무관한 게스트 로그인, 2s 간격). 각 3분.
before = 응답 타임아웃 60s("타임아웃 부재"의 근사 — 서킷 설정은 동일) / after = 기본값(3s + 서킷).
게스트 IP 리밋은 실험 대상이 아니므로 env로 완화.

## 판정: 성공 — 무관한 경로로의 전염이 26배 축소

| 지표 | before (60s) | after (3s+서킷) | 개선 |
|---|---|---|---|
| 방관자(게스트) avg | **1.00s** | **38.5ms** | 26× |
| 방관자 max | **58.2s** (스레드 고갈 인질) | **1.37s** | 42× |
| 방관자 성공률 | 100% (지연, 죽진 않음) | 100% | |
| 카카오 로그인 max | 63s | 4.68s (3s×2회 시도+큐잉) | |
| 서킷 즉시 거절(503) | 112,707건 | 166,842건 | med ~5ms 흡수 |
| 업스트림 실패(502) | 4 | 0 | |

after: 초당 ~920건의 공격이 med 5.7ms의 503으로 튕겨나가는 동안(외부 호출도 스레드 점유도 없음)
게스트 로그인은 p95 27ms로 평온 — 카카오가 죽어도 앱의 나머지는 모른다.

## 가설과 달랐던 것 — 그리고 더 좋은 발견

가설: "before에선 서킷이 ~60초간 장님이다(호출이 끝나야 표본을 세는데 60초간 안 끝나므로)."
실측: 양쪽 다 서킷이 거의 즉시 열렸다 — before의 502가 4건뿐이고 사실상 전 공격 반복이 503.
원인: 가짜 서버(파이썬 ThreadingHTTPServer)의 accept 백로그(기본 5)가 200 동시 연결을 다 받지
못해 일부를 즉시 리셋했고, 이 빠른 연결 실패들이 서킷 표본을 조기에 채웠다.

이 우연이 역할 분담을 더 선명하게 증명했다: **서킷은 "새 호출"만 막는다. 이미 나가서 스레드를
쥔 호출(인질)은 타임아웃만이 회수한다.** 서킷이 열려 있었는데도 before의 방관자 max가 58.2s인
이유 — 최초 ~200개 인질이 60초 타임아웃까지 톰캣 스레드를 쥐고 있었다. after는 같은 인질을
3초 만에 회수했다(max 1.37s). 타임아웃 없이는 서킷만으로 스레드풀을 지킬 수 없다 — 둘은 세트다.

## p95의 함정 (읽는 법)

before의 방관자 p95는 25ms로 정상처럼 보인다 — 마비가 첫 ~60초(런의 1/3)에 국한되고 느린
표본이 전체의 ~3%라 분위수에 잡히지 않은 것. avg(1s)와 max(58.2s)가 진실을 말한다.
구간 장애의 영향은 전체 분위수가 아니라 avg·max·시계열로 봐야 한다.

## 한계 (기지)

- before는 #125 이전 코드가 아니라 "타임아웃 60s 근사"다(이전 코드는 URI 주입이 불가해 가짜
  카카오를 붙일 수 없음 — 측정 가능성 자체가 이번 에픽의 산물). 서킷도 켜진 채였으므로 위
  표는 주로 "타임아웃의 효과"를 격리한 것이고, 서킷의 효과는 503 흡수량(11만~16만 건)으로 관측.
- 가짜 서버 백로그의 조기 리셋이 서킷 개방 시점에 개입 — "순수 침묵"만 재현하려면 backlog 확대 필요.
