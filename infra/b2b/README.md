# B2B 점검 프로젝트 정리 (#174)

2026-10-28에 요청받은 점검 프로젝트 11개만 삭제한다. 실제 축제 `yuja` (`bp_0613bde0c0954e879bc4f3702ad83f88`)와 그 외 프로젝트는 보존한다. **이 문서와 스크립트 작성은 운영 삭제 완료를 뜻하지 않는다.**

## 배포 순서

1. [삭제 작업 테이블 SQL](../../contracts/sql/174-b2b-project-delete.sql)을 운영 DB에 적용한다. 새 테이블 하나를 추가하며 기존 테이블/데이터는 변경하지 않는다.
2. API 변경을 develop → main으로 머지하고 서버 교체 완료를 확인한다. `/v3/api-docs`에 `DELETE /b2b/admin/projects/{id}`가 보여야 한다.
3. 아래 미리보기로 ID·slug·상태를 확인한 뒤 실행한다. Studio 키는 실행 환경의 서버 시크릿을 사용하고 문서/명령 인자/저장소에 적지 않는다.

## 미리보기와 실행

Python 3 표준 라이브러리만 사용한다. 저장소 루트에서 실행하며, `STUDIO_KEY` 환경 변수가 없으면 화면에 표시되지 않는 입력을 받는다.

```powershell
python scripts/b2b_cleanup_test_projects.py
python scripts/b2b_cleanup_test_projects.py --execute
```

기본 동작은 조회만 수행하는 미리보기다. 삭제 대상은 스크립트에 명시된 ID·slug 11쌍이며 이름 접두사로 대상을 늘리지 않는다. 모든 대상의 상태를 먼저 검사하고 LIVE, ID/slug 불일치, yuja 누락이면 아무것도 삭제하지 않고 중단한다. 각 DELETE 직전에 대상과 yuja를 다시 확인한다. 이미 없는 대상은 건너뛰어 중간 실패 후 재실행할 수 있다. 다른 ID가 같은 slug를 차지하면 중단한다. 자동 pause는 하지 않는다.

실행 기록은 기본적으로 시스템 임시 디렉터리의 `b2b-cleanup-시각.json`에 저장한다. 키/HTTP 헤더는 기록하지 않는다. 실패 시 이미 삭제한 ID와 중단 원인을 보고 나머지를 확인한다. 삭제된 대상 단건 GET의 404, 최종 목록에서 11개 부재, yuja 및 기존 비대상 프로젝트의 응답 보존을 검증한다. 최종 검증 중 동시 편집이 감지돼도 완료로 보고하지 않는다.

## 실제 파일 정리 확인

204는 프로젝트와 네컷 DB 삭제 및 저장소 삭제 작업 기록의 커밋을 뜻한다. 커밋 직후 파일 정리를 시도하고, 실패하면 `b2b_asset_deletions`에 남겨 5분 뒤 재시도한다. 기본 배치 주기는 60초다. 공유된 프레임 사본은 다른 프로젝트/네컷의 참조가 남아 있으면 보존하며, 카탈로그 원본도 유지한다. 이미 CDN에 캐시되거나 사용자가 내려받은 이미지의 즉시 회수는 포함하지 않는다.

운영 DB에서 `b2b_asset_deletions`에 남은 작업과 `B2B asset deletion pending` 로그를 확인한다. 작업이 남았다면 저장소 정리 완료로 보고하지 않는다. 배포 전 스냅샷 등 운영의 기존 복구 절차는 그대로 따른다. 이 기능은 삭제 취소 API를 제공하지 않는다.

## FE 계약

- 기존 관리자 서버 프록시와 인증을 통해 `DELETE /b2b/admin/projects/{id}` 호출.
- DRAFT/PAUSED에서만 삭제 버튼 활성화. LIVE는 먼저 참여 중단 안내.
- 확인창: 프로젝트와 모든 네컷이 삭제되고 기존 공유 링크도 사용할 수 없음을 명시.
- 204에는 본문이 없으므로 JSON을 파싱하지 말고 목록으로 이동/재조회.
- 404는 이미 삭제됨, 409는 상태 변경/LIVE 안내. 오류 형식은 기존 `{status,message}`.
- 일반 삭제 API에 yuja를 하드코딩해서 금지하지 않는다. 이번 점검 스크립트가 yuja와 비대상 프로젝트를 보호한다.
